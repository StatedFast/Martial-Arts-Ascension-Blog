这块看板想证明什么
  1. 堆内与堆外是两堵不同的墙：heap 撞 -Xmx 抛 OutOfMemoryError: Java heap space； direct 撞 MaxDirectMemorySize 抛 OOM: Direct buffer memory， 而 -Xmx 再大也拦不住后者。
  2. 「内存没涨」不等于「没泄漏」：堆外内存 MemoryMXBean 照不到， 得看 BufferPoolMXBean —— 曲线里那条蓝线。
  3. 修复的本质是「有界」：把无界缓存换成有界 LRU，曲线立刻走平， 代价是命中率下降，不是免费的。
  4. GC 是前兆不是判决：泄漏后期真正先尖起来的是 GC 次数与停顿耗时， 而不是占用率本身。
撞墙时按这六步查
  1. 看异常文案：heap space / Direct buffer memory / metaspace —— 先确定是哪堵墙。
  2. 对齐时间轴：OOM 前 5 分钟的曲线形状（阶梯上涨 = 泄漏，尖刺 = 突发大对象）。
  3. 查 GC 日志：Full GC 频繁且回收量小 → 存在强引用链，不是「GC 没干活」。
  4. 堆内用 jmap -histo:live 看 Top 对象；堆外用 NMT / MaxDirectMemorySize 反推。
  5. 找持有者：MAT 看 GC Roots 引用链，定位到具体缓存 / 集合字段。
  6. 改法只有两类：限制生命周期（有界缓存、WeakReference、及时 release），或放大边界（调参数，治标）。
